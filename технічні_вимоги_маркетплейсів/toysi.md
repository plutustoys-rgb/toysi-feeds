# Toysi.ua — API постачальника (order_create) — довідник

Джерело: `https://toysi.ua/api-doc.php` (живо звірено 2026-09-25) + історія інцидентів у
`order_router.py`/`toysi_order_submit.py`. Toysi — НЕ маркетплейс, а наш постачальник (дропшип):
через їхній API ми СТВОРЮЄМО замовлення (`order_create`), вони пакують+відправляють.

## order_create — усі POST-параметри (апідок, 2026-09-25)

| Параметр | Тип | Опис (апідок) |
|---|---|---|
| `api_version` | int | завжди `1` |
| `api_method` | str | `"order_create"` |
| `auth_user` | str | ID користувача з ЛК |
| `auth_key` | str | секретний ключ з ЛК (той самий, що й для XML-фіда) |
| `internal_order_id` | str | наш унікальний номер, ≤25 символів |
| `positions_count` | int | кількість позицій, ≤1000 |
| `positions_quantity` | array | `positions_quantity[код]=кількість` (PHP-стиль) |
| `comment` | str, optional | ≤500 символів |
| `shipping_warehouse_id` | int | номер відділення перевізника; `0` = доставка за адресою. **Toysi вимагає це поле ЗАВЖДИ присутнім у POST**, навіть коли 0 — без нього `response_code=4`, попри те що документація описує поле як optional (перевірено емпірично) |
| `shipping_carrier_name` | str | назва перевізника; **приймає ЛИШЕ точний рядок `"Новая почта"` (рос.)** — `"Нова Пошта"` (укр.) відхиляється як невідомий перевізник (`response_code=4`, без пояснення чому). Для самовивозу — `"toysi"` |
| `shipping_city` | str | **«Город доставки. Желательно с областью и районом, чтобы исключить ситуации, когда город клиента может оказаться не тем, что у перевозчика»** — дослівно з апідоку. Це не декоративне уточнення, а задокументований захист від саме того класу помилки, що стався 24.09 (див. «Інцидент» нижче) |
| `shipping_city_id` | str | «Идентификатор города по справочнику городов перевозчика. Необязательный в случае адресной доставки. **В случае доставки на отделение перевозчика — обязательно указывать**» — по факту ми передаємо NP CityRef (GUID), коли площадка дала його структурно; Toysi приймає без помилки, але **живе підтвердження менеджера (24.09.2026): «маршрутизація йде лише за містом»** — тобто це поле, попри документовану «обов'язковість», НЕ впливає на фактичний вибір відділення в їхній системі. Далі слати варто (документована вимога), але покладатись на нього як на єдиний захист — не можна |
| `shipping_address` | str | «Обязательный параметр. Но может быть пустой строкой, если `shipping_warehouse_id>0`» |
| `shipping_firstname` / `shipping_lastname` | str | обов'язкові |
| `shipping_middlename` | str, optional | |
| `shipping_phone` | str | 12 цифр з `"380..."`, БЕЗ `+`/пробілів/дефісів (перевірено на замовленні №414634349, `response_code=16` без цього) |
| `shipping_dt` | str | бажаний час доставки, `"YYYY-MM-DD HH:MM:SS"` |
| `shipping_moneyback` | float | сума накладеного платежу, UAH |
| `shipping_declared_value` | int, optional | оголошена вартість, мінімум 500 |
| `redirect_url` | str, optional | — |
| `api_mode` | str, optional | `"test"` — замовлення НЕ обробляється менеджером, не списує депозит, не з'являється в Історії замовлень (ефемерне; не плутати з реальним прогоном) |
| `ttn` | str, optional | номер ТТН |

**Область/район — окремого поля НЕМАЄ.** Апідок прямо каже: деталізацію області й району треба
класти ВСЕРЕДИНУ значення `shipping_city` (не в окреме поле, якого просто не існує).

## response_code (order_create)

| код | значення |
|---|---|
| 1 | Замовлення прийнято |
| 2 | Дублікат `internal_order_id` — дані повертаються без створення нового (вважати успіхом) |
| 3 | Створення не вдалося — рекомендовано повторити |
| 4 | Відсутні обов'язкові POST-параметри |
| 5 | Невірний `auth_user`/`auth_key` |
| 6 | `internal_order_id` >25 символів |
| 7 | Невірна кількість позицій |
| 8 | `positions_quantity` не масив/порожній |
| 9 | Довжина `positions_quantity` ≠ `positions_count` |
| 11 | Коди товарів відсутні в базі Toysi |
| 12 | Нецілі ключі в `positions_quantity` |
| 13 | Невірна кількість товару |
| 14 / 15 | Порожнє ім'я / прізвище отримувача |
| 16 | Невірний телефон отримувача |
| 17 | Невірний час доставки |
| 18 | Невірна сума накладеного платежу |
| 19 | Порожня назва перевізника |
| 20 | Порожня адреса доставки |
| 21 | Порожнє місто доставки |

Код `10` навмисно відсутній у таблиці `response_code` (перевірено напряму на apidoc) — не пропуск.
Це ІНША таблиця, ніж коди поля `status` замовлення (order_status/order_positions, окремо —
`10` там означає «Скасовано»); легко переплутати, бо обидві звуться "код 10".

## Інцидент 2026-09-24 — EVA 8-081747967, «Південне»→«Южное»

Клієнт замовляв на Відділення №1, смт Південне (Харківська обл., Харківський р-н). Ми передали
`shipping_city="Південне"` (гола назва, без області/району — попри те що апідок прямо радить
інакше) + коректний `shipping_city_id` (NP CityRef) + `shipping_warehouse_id="1"`. ТТН пішла на
Відділення №1 у м. Одеса (у картці замовлення Toysi поле «Город» показало **«Южное»** — інший,
одеський населений пункт з такою ж назвою).

**Toysi-менеджер (живо, 25.09.2026) підтвердив:** *«Маршрутизація йде лише за містом. Може
виникати така ситуація що є міста з однаковою назвою і тому підтягується інша область. Для
уникнення таких ситуацій ми рекомендуємо робити замовлення вручну.»* — тобто `shipping_city_id`
попри документовану «обов'язковість для доставки на відділення» РЕАЛЬНО не використовується їхньою
системою для розрізнення однойменних міст; єдиний робочий захист — те, що апідок і так радив від
початку: клади область/район ПРЯМО в `shipping_city`.

**Виправлено (`order_router.py::build_toysi_order`, 2026-09-25):** `shipping_city_name` тепер несе
повну локацію (`місто, район р-н, область обл.` — та сама конструкція, що раніше йшла лише в
`comment`), а не голу назву міста. Старе припущення в коді («в назву міста район класти не
можна — зламає Ref-матч перевізника») ніде в апідоку не підтверджене й було прибране разом із
фіксом.

## RZ-Delivery (Rozetka) — перевізник у замовленні Toysi

**НЕ намагатись знову «полагодити» без нового прямого підтвердження Toysi.** Історія (`order_router.py`
git log, PR #360→#361, 2026-08-21):
- Спроба 1 (PR #334): `shipping_carrier_name="Rozetka"` — Toysi підтвердив, що їхня CRM не
  розпізнає цей рядок і тихо фолбечить на «Новая почта» + треба вручну виправляти.
- Спроба 2 (PR #360): `shipping_carrier_name="toysi"` + `shipping_warehouse_id=1` (самовивіз,
  документоване значення «без зовнішнього перевізника») — Toysi відповів, що синхронізацію
  Rozetka на своєму боці НЕ робитимуть, і попросив «лишити як є» (Новая почта + коментар).
- PR #361: відкат до Спроби 1 (`"Rozetka"`), за прямим проханням Toysi.

Скарга менеджера 25.09.2026 («замовлення по Rozetka надходять у полі Нова Пошта, виправляємо
вручну») — це ТОЙ САМИЙ, уже узгоджений і прийнятий компроміс, не новий баг. Код міняти без
нового явного «так, зробіть X» від Toysi — не варто (повторення того самого циклу здогад→відкат).

## Наскрізний аудит 2026-09-25 (вимога власника — усі площадки, не лише EVA)

За прямою вимогою власника («з усіх площадок повинно правильно передаватися Тойсі з урахуванням
їх вимог») проведено повний, не точковий аудит `build_toysi_order`/`toysi_order_submit`/конвертерів
усіх площадок. Знайдено й виправлено (того ж дня):

1. **`settlement_raion()` викликався БЕЗ `settlement_ref`**, хоча точний NP-реф (`np_city_ref`)
   часто вже відомий на момент виклику — функція без ref повертає `""` для будь-якого села, що має
   тезку в ТІЙ САМІЙ області (власний приклад функції: Троїцьке, Одеська обл. — Біляївський vs
   Любашівський р-н), навіть коли реф уже знімає неоднозначність. `order_router.py::build_toysi_order`
   тепер передає `city_ref` у `settlement_raion(city, settlement_ref=city_ref, area_hint=area_hint)`.
2. **`positions_quantity` (toysi_order_submit.py) губив qty при дублікаті `toysi_code`** у позиціях
   (dict-компрегенція перезаписувала останнім входженням), а `moneyback` рахував повну суму за
   ВСІМА позиціями, дублі включно → Toysi стягнув би повний накладений платіж, відвантаживши менше
   одиниць. Тепер qty СУМУЄТЬСЯ за кодом, `positions_count` рахує унікальні коди.
3. **Сайт (`site_order_api.py`) ніколи не передавав область у `np_branch`** — фронт (`app.js`)
   показував область у підказці автокомпліту, але на виборі зберігав лише голу назву міста.
   Тепер `selectedCityArea` (з НП `AreaDescription`) іде в POST `np_city_area`, бекенд будує
   `np_branch` у форматі `"Місто (Область обл.), Відділення"` — тому самому, що й Prom/Rozetka.

Регрес-тест: `test_toysi_city_area_fixes.py` (9 перевірок, усі три фікси).

**Перевірене й ПІДТВЕРДЖЕНО коректне** (аудит, не змінювалось): `shipping_carrier_name` завжди
точно `"Новая почта"` для НП-замовлень усіх площадок; нормалізація телефону централізована, без
обхідних шляхів; `toysi_code`-мапінг платформо-коректний (EVA `item.id`, не `sku`/`article`; Prom
`sku`/`external_id`; Rozetka `article`/`price_offer_id`); `response_code` 2 всюди трактується як
успіх; `find_city`/`find_warehouse` підтверджено мертві в потоці замовлень (лише коментарі +
`nova_poshta.py`'s власний `__main__`).

**Невирішений, задокументований ризик (не код-баг, а межа знання):** новий формат `shipping_city`
(місто+район+область одним рядком) ще НЕ підтверджений живим прогоном через Toysi — апідок радить
класти область/район туди, але чи їхній матчинг справді толерує довший/складніший рядок (а не
точний список назв) — невідомо без живого замовлення. Перше замовлення з довгим `shipping_city`
варто звірити вручну в кабінеті Toysi.
