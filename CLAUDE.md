# CLAUDE.md — toysi-feeds (авто-завантажується Claude Code на старті кожної сесії)

## Що це

Фід-пайплайн + репрайсер + order pipeline для дропшип-магазину іграшок (Toysi.ua → Prom/Rozetka/EVA/ALLO/Google/Meta/Bing). Три рівнозначні цілі: надійність, автономність, видимість.

## Гілки

- `master` — код
- `feed-data` — публічні фіди + стан-файли. **Публікується orphan force-push (git checkout --orphan + git rm -r --cached . + force-push) — переписує ВСЕ щоразу, без історії.** Будь-який файл, доданий лише умовно (best-effort крок), зникає НАЗАВЖДИ, якщо генерація цього прогону впаде/поверне порожній файл, і немає симетричного restore-кроку. `rozetka_feed.xml`/`prom_feed_top.xml` мають такий restore-фолбек; `google_merchant_feed.xml`/`meta_feed.xml`/`bing_feed.xml`/`eva_feed.xml` — НЕ МАЮТЬ (відомий незакритий ризик, вже спричинив реальний інцидент з Google Merchant Center 2026-07-27).
- `scan-state-data` — стан нічного конкурентного скану (публікує VPS)
- `catalog-sync-delisted-data` — стан delisted SKU від VPS catalog sync (публікує VPS)

**Правило для нового публікованого файлу в будь-яку з цих гілок:** якщо генерація best-effort — обов'язково додай restore-крок (`git show origin/BRANCH:path > path`, якщо файл цього прогону порожній/відсутній), інакше файл рано чи пізно зникне без сліду.

## VPS (45.94.157.4)

Усі Python-скрипти виконуються через `/opt/plutustoys/venv/bin/python3` (venv з встановленими залежностями, зокрема `python-dotenv`). Голий `python3` у systemd `.service`-файлі резолвиться в системний Python без залежностей і падає — перевіряй це в КОЖНОМУ новому `.service`-файлі: або абсолютний шлях до venv-python в `ExecStart`, або явний `Environment=PATH=/opt/plutustoys/venv/bin:/usr/bin:/bin` перед ним.

**Ти НІКОЛИ не виконуєш SSH/SCP на VPS сама** — класифікатор середовища блокує вихідні з'єднання на довільні хости завжди, незалежно від дозволу власника в чаті. Це структурна межа інструмента, не політика. Read-only deploy-ключі ти реєструєш сама через `gh api` — успішно. Write-scoped ключі — класифікатор блокує, реєстрація завжди вручну власником; твоя робота — підготувати точну команду й публічний ключ, передати їх явно, не тримати "в голові".

## Rozetka

Rozetka НЕ має власної історії продажів. Жодна функція відбору/ранжування/ротації для Rozetka не повинна перевикористовувати Prom-логіку (`select_top_items()` тощо) — це необґрунтована аналогія, двічі прямо відхилена власником. Поточна модель: повністю статичний список (`rozetka_static_selection.json`, round-trip через `feed-data`), без жодної live-перевірки (включно зі складом), поки SKU не пройшов модерацію Rozetka.

## Процес PR

Кожен PR проходить незалежну аудит-сесію ("Security audit: rozetka_agent") перед мержем, без винятку — незалежно від розміру. Аудит перевіряє живо (git show, синтетичні тести), не на слово з опису PR. Не мержити самостійно без явного висновку аудиту чи прямого "так, мерж" від власника.
